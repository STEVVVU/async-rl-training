# Matched head-only study

The opt-in adapter extends the local reference without changing the default four-update `drive` contract. Its frozen manifest contains 35/10/10 canonical train, validation, and test pairs, shuffled once with seed 421. Five paired seeds use the same 512-group arithmetic schedule per seed. Both arms run 256 updates with two groups per update, LR 0.005, baseline 0.5, ratio clipping 0.8 to 1.2, and maximum policy age one. Async continuations keep their group RNG and action budget across a version; generated, accepted, stale, tail, token, and per-group version counts are retained.

Run the phases explicitly from the repository root with the existing interpreter. Each directory must be new for preparation.

```powershell
& $uv run --isolated --no-project --python $ml -- cmd.exe /d /c $ml scripts/verify_async_rl.py study-prepare --study .evidence/matched-study
& $uv run --isolated --no-project --python $ml -- cmd.exe /d /c $ml scripts/verify_async_rl.py study-run --study .evidence/matched-study
& $uv run --isolated --no-project --python $ml -- cmd.exe /d /c $ml scripts/verify_async_rl.py study-select --study .evidence/matched-study
& $uv run --isolated --no-project --python $ml -- cmd.exe /d /c $ml scripts/verify_async_rl.py study-test --study .evidence/matched-study
```

Preparation caches BF16-backbone hidden features for train and validation prompts, while storing features in FP32 and casting them back to BF16 at sampling/evaluation. Test prompts are not read before the frozen selection. Full-model digit logits must match cached-feature logits within one BF16 ULP (with a `1e-42` absolute floor only around zero) for both constrained projections used by the policy: two tool rows and ten answer rows. Preparation, initial, checkpoint, and test receipts retain maximum ULP and absolute error separately for each projection. No tolerance adjustment is allowed after a run. Both arms run with installed BF16 output rows, float32 sampling logits, and an FP32 master head with differentiable BF16 update forwards. The same per-group Torch RNG makes coroutine scheduling independent of random streams.

The fixed schedule has 256 updates and two accepted groups per update. Sync generates and accepts 512 groups with 2,048 action tokens, all at the current version. Async generates 514 groups and accepts 512, retaining two partial groups at the tail; it records 2,056 action tokens, 510 mixed-version accepted groups, and per-action versions. Generated, accepted, stale, tail, action/prompt token, mixed-version, terminal decision, and per-UID ledgers are validated before a run receipt can pass. Runs are interleaved by seed, reversing arm order on alternating seeds. Timed training uses CUDA synchronization around monotonic wall-clock intervals. Model load, preparation, validation, consistency checks, and checkpoint writes are recorded separately.

Checkpoints at updates 32, 128, and 256 are native safetensors and are exactly reloaded. Selection requires all ten run receipts and all three checkpoints per run, verifies metric and checkpoint hashes plus source/model/config identities and every run's manifest, feature, prompt, and preparation hashes against current prepared files, then selects by validation expected reward only with earliest step as the tie-break. It reports expected reward and answer success, initial and selected per-pair results, and paired seed deltas; a negative improvement remains valid. The separate final-test action recomputes selection and verifies every candidate hash before it reads test prompts. It fails if a test receipt already exists. Test quality is descriptive and may be negative.

This path is head-only cached-feature policy training, with an FP32 master head installed into BF16 model rows. It records the cached model config/weight/tokenizer hashes, runtime, trainable parameter count, and source identity. The driver requires 10 GiB free disk, 8 GiB available system memory, and 4 GiB free CUDA memory. It runs in one process and one asyncio event loop; CUDA kernels serialize. It does not measure native SkyRL, concurrent GPU throughput, or full-model fine-tuning.
